# 01 — Comprehension science for a canvas-based review of agent work

Research date: 2026-10-27. Scope: what program-comprehension, spatial-IDE, visualization and recent human-AI studies say about how a person should review an AI agent's "view configuration" work on a zoomable canvas (current flow, proposed change, actual change, variants, tests, diffs, comments) for code and non-code step graphs (low-code SQL/JS chains, UI page designers).

Not repeated here (covered in an earlier pass): code review size limits, overreliance/cognitive forcing, explanation studies, NN/g progressive disclosure, Microsoft HAI guidelines, Copilot Workspace.

**Reading-depth legend** — `FULL` = I read the full text this pass; `PARTIAL` = I read substantial sections; `ABSTRACT` = abstract/landing page/search snippet only; `PRIOR` = well-known canonical work cited from prior knowledge, not re-read this pass (claim kept to the widely-reported core).

## 1. Spatial / canvas code comprehension

| # | Claim | Source | Depth | Implication for the canvas app |
|---|---|---|---|---|
| 1.1 | Code Bubbles (lightweight, editable fragments arranged as concurrently visible "working sets") reduced navigation interactions and improved understanding time vs. Eclipse on two controlled tasks. | Bragdon et al., CHI 2010 — https://www.eecs.ucf.edu/~jjl/pubs/p2503-bragdon.pdf | ABSTRACT | Show the *working set relevant to the change* (fragments: steps, SQL bodies, UI components), not whole files/whole graphs. The unit on the canvas should be a fragment. |
| 1.2 | Debugger Canvas (industrial Code Bubbles, 14k+ downloads): users found it most useful for long/complicated call paths, layered systems, unfamiliar code and indirect control flow (factories, DI); not worth it for small, quick checks. | DeLine et al., ICSE 2012 SEIP — https://www.microsoft.com/en-us/research/publication/debugger-canvas-industrial-experience-with-the-code-bubbles-paradigm/ | FULL | Our sweet spot is exactly "unfamiliar, multi-step, indirect" (agent-written step chains). But small changes should not force the full canvas — offer a lightweight path (plain diff / single card) for trivial reviews. |
| 1.3 | Auto-creating a new canvas per debugging session was the top usability problem — users called the result "clutter"; fix was one shared canvas unless the user explicitly makes a new one. | Same (RITE study, 10 participants) | FULL | Do not spawn a new canvas/board per iteration or per agent run. Variants should live inside one persistent review space, created on explicit action. |
| 1.4 | Of 19 users who abandoned Debugger Canvas, the reasons were mostly bugs/performance (14 of 27 mentions) and *undiscovered features* (6 mentions — users complained about missing features that existed). | Same, Table 2 | FULL | Performance and discoverability matter more than novel layout ideas. Budget for fast rendering of large graphs and make key navigation (jump to change, next comment) visible, not hidden gestures. |
| 1.5 | The canvas "is best embodied as a mode within the existing user experience"; v2 added a toggle to switch to the canvas mid-session; users still wanted "the rest of the file" (fields, adjacent code). | Same, Conclusions §VII | FULL | Always offer an escape hatch from a fragment to its full source context (whole SQL step, whole page JSON, whole file) and to a conventional linear diff. |
| 1.6 | Familiar file layout competes with canvas layout: "you know that this function is right above this, then it messes with your mind when it is in the bubbles." | Same, interviews | FULL | Where the target system has its own native layout (UI page designer, step order in a chain), reuse it on the canvas rather than inventing a new arrangement. |
| 1.7 | Two of 11 interviewees valued the canvas for *communicating* a fix to teammates ("show how you made the change, how you got it, what modules were impacted"). | Same | FULL | The canvas is also a shareable artifact: a reviewer should be able to link to a region/state; comments anchored to canvas positions are worth it. |
| 1.8 | Code Canvas proposed one infinite zoomable surface with semantic zoom (detail drops as you zoom out, down to UML-like boxes) to exploit spatial memory and avoid "bento box" IDE panes. | DeLine & Rowan, ICSE 2010 NIER — https://www.microsoft.com/en-us/research/publication/code-canvas-zooming-towards-better-development-environments/ | ABSTRACT | Vision paper; no controlled evidence. Treat semantic zoom as plausible, not proven. |
| 1.9 | Code Thumbnails: navigation by symbol names loads working memory; spatial cues (file thumbnails) can aid navigation. | DeLine, Czerwinski et al., 2006 — https://microsoft.com/en-us/research/uploads/prod/2006/09/Using-Spatial-Memory-to-Navigate-Source-Code.pdf | ABSTRACT | Small, stable visual "fingerprints" of nodes (shape/colour/mini-preview) help re-finding. |
| 1.10 | Patchworks (fixed grid of "patches" on a ribbon) reduced navigation time and errors vs. Eclipse in a prior study; a simulation found the arrangement strategy within the grid didn't matter much — what mattered was having multiple fragments visible in a predictable structure. | Henley et al., VL/HCC 2014 — https://austinhenley.com/pubs/Henley2014VLHCC_Patchworks.pdf | ABSTRACT | A *constrained* layout (grid/lanes) may be as good as free-form and is cheaper/less cluttered. Consider lanes (current / proposed / actual / variant N) instead of free placement. |
| 1.11 | Codemap (Software Cartography) pilot: layout from lexical similarity failed — developers read spatial distance as *structural dependency*, expected the map to match their architecture mental model, and didn't use the map's axes. | Kuhn, Erni, Nierstrasz, SOFTVIS 2010 — https://arxiv.org/abs/1001.2386 | ABSTRACT (+ snippets of results) | Proximity on the canvas will be read as "these are related/connected". Place things near each other only if they are structurally related (data flow, call, containment). Never lay out by an arbitrary metric. |
| 1.12 | Controlled experiment (n=20): a spatial code canvas vs. tabs showed **no significant effect on comprehension performance**; it changed how time was spent (navigation, annotation, UI interaction). | Bouraffa, Fuhrmann, Maalej, ICSE 2023 — https://arxiv.org/abs/2304.09301 | ABSTRACT | Honest caveat: the canvas itself is not a proven comprehension booster. Its value must come from *what* it puts side by side (current/proposed/actual, test ↔ step), not from spatiality per se. |

## 2. Program comprehension models — what does a reviewer need first?

| # | Claim | Source | Depth | Implication |
|---|---|---|---|---|
| 2.1 | Brooks: comprehension is top-down hypothesis-driven — the programmer forms hypotheses about the domain and verifies them against code, using **beacons** (recognisable cues indicating a known operation/structure). | Brooks 1983, IJMMS (PRIOR); summary in https://sites.cc.gatech.edu/reverse/repository/cogmodels.pdf | PRIOR / ABSTRACT | Lead with the *intent/hypothesis* ("this change adds a retry around the payment step"), then let the reviewer verify against concrete fragments. |
| 2.2 | Experts rely on beacons and concentrate on important regions; novices discriminate little between regions. | Crosby, Scholtz, Wiedenbeck, PPIG 2002 — https://ppig.org/papers/2002-ppig-14th-crosby/ | ABSTRACT | Visually surface beacons for non-code steps too: step type icons, SQL verb (INSERT/DELETE/UPDATE), external calls, side effects. Highlighting "risky beacons" helps less-expert reviewers. |
| 2.3 | Soloway & Ehrlich: experts use programming plans and discourse rules; plan-violating code slows experts dramatically. | Soloway & Ehrlich 1984, IEEE TSE (PRIOR) | PRIOR | Agent output that violates the conventions of the low-code platform should be flagged — conventions are what reviewers lean on. |
| 2.4 | Integrated model (von Mayrhauser & Vans): maintainers switch opportunistically between a domain model (top-down), situation model, and program model (bottom-up), at all levels of abstraction. | von Mayrhauser & Vans, IEEE Computer 1995 — https://www.cs.kent.edu/~jmaletic/cs69995-PC/papers/von_mayrhauser-1995.pdf | ABSTRACT | The canvas must support *fast switching between levels* (system flow ↔ step ↔ SQL body) without losing place. Neither pure top-down nor pure bottom-up flows suffice. |
| 2.5 | Information Foraging Theory (debugging): navigation is predicted by **scent** (cue words linking where you are to your goal) and **topology** (what links exist); professional programmers' verbalisations concerned scent-following far more than hypotheses; an IFT model predicted navigation better than models without scent. | Lawrance et al., IEEE TSE 2013 — https://web.engr.oregonstate.edu/~burnett/Reprints/TSE-IFT-2013-asprinted.pdf | ABSTRACT | Every link/edge/collapsed node needs strong scent: meaningful labels ("calls `charge_card`, writes `orders`") instead of "Step 7". Collapsed summaries are scent; make them informative. |
| 2.6 | Fleming et al. extend IFT to debugging, refactoring and reuse tools: tools succeed when they raise scent quality and reduce navigation cost between patches. | Fleming et al., TOSEM 2013 — https://digitalcommons.memphis.edu/facpubs/2490 | ABSTRACT | Provide cheap "between-patch" links: from a test case to the steps it exercises; from a diff hunk to its node on the flow; from a comment to its anchor. |
| 2.7 | Ko et al. and Sillito et al.: developers' work is seek → relate → collect; their questions progress from finding focus points to building understanding of relationships across subgraphs. | Ko et al., IEEE TSE 2006; Sillito, Murphy, De Volder, FSE 2006 (PRIOR) | PRIOR | Order the review: (1) where are the focus points (changed nodes), (2) how they relate to neighbours (callers/consumers), (3) collect evidence (tests, outputs). |

**What a reviewer needs first (synthesis):** a short statement of intent + the changed focus points located on the overall flow (the "where"), with high-scent labels; then the ability to drop to concrete fragments to verify (beacons). This is consistent with Brooks, IFT, and Sillito, and with the Shneiderman mantra below.

## 3. Visualization fundamentals

| # | Claim | Source | Depth | Implication |
|---|---|---|---|---|
| 3.1 | Visual information-seeking mantra: "overview first, zoom and filter, then details-on-demand." | Shneiderman, IEEE VL 1996 — https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf | PRIOR | Default landing view = whole flow with changes marked. Filters: "changed only", "touched by failing tests", "has unresolved comments". Detail panels on click. |
| 3.2 | Semantic zoom (objects change representation, not just size, with zoom level) was introduced in zoomable UIs (Pad/Pad++). | Bederson & Hollan, UIST 1994 (PRIOR) | PRIOR | Node at far zoom = icon + label + change badge; mid = summary (inputs/outputs, step type); near = full SQL/JS or diff. Never just shrink text into illegibility. |
| 3.3 | Fisheye / focus+context: show local detail in the context of a degree-of-interest-weighted global view. | Furnas, CHI 1986 (PRIOR) | PRIOR | When a step is opened, keep its neighbours and the flow outline visible (minimap or de-emphasised context) instead of a full-screen modal. |
| 3.4 | Multiple coordinated views help when data has diverse attributes, but impose context-switching and screen cost; use them sparingly and keep them linked (brushing/selection propagation). | Wang Baldonado, Woodruff, Kuchinsky, AVI 2000 "Guidelines for using multiple views" (PRIOR) | PRIOR | Selection in one panel (test, diff, flow) must highlight the counterpart everywhere. Limit simultaneous views (~2-4); don't open every artifact at once. |
| 3.5 | Mental map preservation (Misue et al.) — after edits, keep relative positions/orthogonal ordering/proximity stable so users don't relearn the layout. | Misue, Eades, Lai, Sugiyama, JVLC 1995 (PRIOR) | PRIOR | Variants of the same view must share one stable base layout; only changed nodes move/appear. Never re-run a global auto-layout per variant. |
| 3.6 | Evidence on mental map preservation is mixed: preserving it significantly helped **orientation** tasks (find a location/route) — faster, fewer errors — but no conclusive benefit for general comprehension or memorability; users *perceive* it as helpful. | Archambault & Purchase, GD 2012 (https://eprints.gla.ac.uk/66915) and IJHCS 2013 "The 'Map' in the mental map" (https://research.monash.edu/en/publications/the-map-in-the-mental-map-experimental-results-in-dynamic-graph-d/) | ABSTRACT | Stability is justified mainly for *navigating and re-finding* across variants (exactly our case), not as a comprehension silver bullet. |
| 3.7 | Small multiples were significantly faster than animation for dynamic-graph comprehension tasks. | Archambault, Purchase, Pinaud, IEEE TVCG 2011 — https://research.monash.edu/en/publications/animation-small-multiples-and-the-effect-of-mental-map-preservati/ | ABSTRACT | For comparing many variants, a juxtaposed grid/lanes of the same view beats an animated slideshow. |

## 4. Comparing versions

| # | Claim | Source | Depth | Implication |
|---|---|---|---|---|
| 4.1 | All comparison designs are built from three primitives: **juxtaposition** (side by side), **superposition** (overlaid in one frame), **explicit encoding** (compute and show the difference itself); each has tradeoffs (juxtaposition relies on memory/eye movement; superposition clutters; explicit encoding loses the originals). | Gleicher et al., Information Visualization 2011 — https://par.nsf.gov/servlets/purl/10062070 (and https://vivo.colorado.edu/display/pubid_153663) | ABSTRACT | Offer all three explicitly: lanes (current / proposed / actual) = juxtaposition; "overlay mode" on the base flow with added/removed/changed colouring = superposition; change list / textual summary = explicit encoding. |
| 4.2 | L'Yi et al. review 127 comparative-layout papers (15 with user studies) and find terms inconsistently used; whether juxtaposition or superposition wins depends on task. | L'Yi, Jo, Seo, IEEE TVCG 2021 "Comparative Layouts Revisited" — https://arxiv.org/abs/2009.00192 | ABSTRACT | No single comparison mode should be hard-coded; pick default by task ("did the actual match the proposal?" → superposition; "which variant is better?" → juxtaposition). |
| 4.3 | Hierarchical diagram differencing: naive side-by-side dual view performed poorly; dual view **with a difference layer** was most liked; with partially changed layouts, animation and difference layers both helped and the combination was preferred. | Zaman, Kalra, Stuerzlinger, Graphics Interface 2011 — https://vvise.iat.sfu.ca/user/data/papers/versiondiff4diagrams.pdf | ABSTRACT | Never ship plain two-up graph comparison; always colour/badge differences in both panes and link corresponding nodes. |
| 4.4 | Model differencing: abstracting low-level model diffs into high-level change descriptions presented **textually** can beat graph-based diff visualisation for modelers (controlled experiment). | Störrle, MODELSWARD 2013 "Making Sense to Modelers" — https://scitepress.org/Papers/2013/43209/pdf/index.html | ABSTRACT | Pair every graph diff with a generated prose change summary ("Added step `retry_payment` between `charge` and `notify`; changed SQL WHERE in `load_orders`"). Graph-only diffs are not enough for step graphs. |
| 4.5 | Animated transitions between statistical graphics can improve graphical perception; **staged** transitions (one change type at a time) were preferred and helped; avoid unnecessary axis/frame changes. | Heer & Robertson, IEEE InfoVis 2007 — https://homes.cs.washington.edu/~jheer/files/2007-AnimatedTrans-InfoVis.pdf | ABSTRACT (+ secondary slides) | When switching variant A → B in place, animate in stages: removed nodes fade, then moves, then additions; don't pan/zoom the camera at the same time. |
| 4.6 | Counterpoint: animation is often no better than well-designed static graphics (apprehension and congruence problems). | Tversky, Morrison, Bétrancourt, IJHCS 2002 "Animation: can it facilitate?" (PRIOR) | PRIOR | Animation is for continuity/orientation; the comparison judgement itself should rely on static juxtaposition or explicit encoding. |

## 5. Narrative + exploration

| # | Claim | Source | Depth | Implication |
|---|---|---|---|---|
| 5.1 | Narrative visualizations trade off author-driven (strong ordering, heavy messaging, little interaction) vs. reader-driven (free exploration); the **martini glass** puts a short author-driven stem first, then opens into reader-driven exploration. | Segel & Heer, IEEE TVCG 2010 — https://homes.cs.washington.edu/~jheer/files/narrative.pdf | ABSTRACT (+ secondary) | Review sessions should start with a short agent-authored guided tour (intent → changed nodes → evidence/tests → open risks), then release the reviewer onto the free canvas. Tour must be skippable. |
| 5.2 | CodeTour: guided walkthroughs as ordered steps anchored to file/line (or regex pattern), with Markdown descriptions, a `ref` pinning the tour to a commit/tag, and CI checks for "tour drift"; use cases include onboarding and explaining PR/code-review context. | Microsoft CodeTour — https://github.com/microsoft/codetour | FULL (README) | Model the agent's tour as data: ordered steps anchored to node IDs (not positions), pinned to a specific variant/version; detect drift when the anchor node changed after the tour was written. |
| 5.3 | (Weak evidence) No controlled study found comparing guided code tours vs free exploration for review accuracy. | — | — | Treat the tour as a hypothesis; measure (did reviewers who skipped the tour miss more?). Also a risk: an agent-authored tour steers attention — the tour should include "what I did NOT verify". |

## 6. Levels of abstraction (C4)

| # | Claim | Source | Depth | Implication |
|---|---|---|---|---|
| 6.1 | C4 defines four hierarchical zoom levels — System Context, Container, Component, Code — as "maps of your code" at different levels of detail, like zooming in Google Maps; Code level is optional; supplementary diagrams (system landscape, dynamic, deployment) exist. | Simon Brown, https://c4model.com/introduction | PARTIAL | Define a fixed level ladder for our domains, e.g. System (apps/integrations) → Flow (step chain / page) → Step/Component → Body (SQL/JS/props). One diagram per level; semantic zoom moves between them. |
| 6.2 | C4's practical rationale (practitioner, not empirical): mixing abstraction levels in one diagram confuses audiences; different audiences need different levels. | Same (practitioner guidance; no empirical study) | PARTIAL | Do not mix "page designer widget props" with "system integration" on the same zoom level. A reviewer persona (business owner vs. engineer) could pick a default level. Evidence is opinion-grade. |

## 7. Reviewing AI-agent output (2024–2026)

| # | Claim | Source | Depth | Implication |
|---|---|---|---|---|
| 7.1 | Controlled study (Copilot vs OpenHands agent): agents reduced effort and completed tasks users might not finish, but understanding agent behaviour was the key obstacle — 55% said copilot gave better understanding of outputs; agent generations "seemed kind of hidden"; one user "did not expect 10 files ... more than 1000 lines each"; users asked the agent "in what folder have these changes been made?"; authors note understanding output may cost more than writing it. ## Honest assessment of evidence strength

- **Strongest** (controlled studies or large field data): Debugger Canvas field data (clutter, mode-not-replacement, perf/discoverability), Code Bubbles controlled study, Archambault & Purchase on mental-map/orientation and small-multiples vs animation, Lawrance IFT, Chen et al. on agent understanding, Zaman diagram differencing.
- **Mixed / null**: spatial canvas per se did not improve comprehension (Bouraffa 2023); mental-map preservation helps orientation but not general comprehension; animation benefits are contested.
- **Practitioner / theory only**: C4, CodeTour, Shneiderman's mantra, martini glass — widely used design heuristics, not validated for code review.
- **Very new / preprint**: most 2025–2026 agentic-PR studies are arXiv/MSR mining papers read at abstract level only.
- **Gap**: nothing directly on visual review of non-code step graphs produced by agents.

## Top 10 design implications (ranked)

1. **Answer "what did the agent touch, where, how big" first.** Landing view = the overall flow with changed nodes badged, counts and sizes, plus a one-paragraph intent statement (Chen 2025; Shneiderman; Brooks; Sillito).
2. **Pair every graph diff with a prose change summary and a linear diff fallback.** Graph-only and naive side-by-side diffs underperform (Störrle 2013; Zaman 2011; Debugger Canvas "rest of the file").
3. **One stable base layout shared by current / proposed / actual / all variants; never re-layout globally.** Only changed nodes appear/move; use the target system's native ordering where it has one (Misue; Archambault & Purchase 2012; Debugger Canvas familiarity quote).
4. **Offer the three comparison modes explicitly** — lanes (juxtaposition), overlay on base (superposition), change list (explicit encoding) — and pick defaults per task (Gleicher 2011; L'Yi 2021). For many variants, prefer small multiples over animation (Archambault 2011).
5. **Proximity means relationship.** Place nodes near each other only for real structural relations (data flow, call, containment); never arbitrary metrics (Kuhn Codemap 2010).
6. **High-scent labels and links everywhere.** Collapsed nodes, edges and test cases need descriptive labels (tables written, calls made); one-click links test ↔ step ↔ diff hunk ↔ comment (Lawrance/Fleming IFT).
7. **Fixed level-of-abstraction ladder with semantic zoom** (System → Flow → Step → Body), one level per zoom band, with focus+context when opening detail (C4; Bederson; Furnas; von Mayrhauser & Vans switching).
8. **Martini-glass review: short, skippable agent-authored tour anchored to node IDs and pinned to a version, then free exploration;** include what the agent did not verify; detect tour drift (Segel & Heer; CodeTour).
9. **Avoid clutter by construction:** one persistent review space, explicit creation of new variants/boards, limited simultaneous coordinated views, fast performance, discoverable navigation (Debugger Canvas; Baldonado guidelines).
10. **Counter passive approval with per-node review state** (unseen / skimmed / verified / commented) and prominent verification evidence; support review checkpoints at the plan stage, not only the end (Balepur 2026; 2601.20106; Huang 2025; Chen 2025). Plus: the canvas itself isn't proven to improve comprehension (Bouraffa 2023), so run our own defect-finding usability test early.
